Decide First

The landing page stops selling and starts deciding. A stranger arrives, answers four cheap questions, and gets one meal they can actually cook — before we ask for an email. Signing up is then an upgrade of something they already hold, not a toll gate in front of it.

06 · One meal, one decision

What must be on it

  • The name, big. Display type, no hedging — "Ewa agoyin with dodo", not "you might like…".
  • Why this, in one line. Written by the model, grounded in the answers: "Hot day, forty minutes, and the beans are already in your kitchen."
  • Have / need, split. Straight from MealMatch — ingredients[] with enough, low, missing.
  • Provenance mark. grape when the framing is model-written; the meal itself is always ours.
  • Two alternates, collapsed. "Something else" re-ranks locally — no second AI call.
  • A way out that is not a restart. "Not this" rejects this dish and re-decides without it; "Change an answer" reopens one step. Both are free. See §07.
This card becomes a story later Once meal photography exists, this single card becomes the first of three swipeable cards, each with a real image and a one-line pitch. The verdict stays the verdict — card one is still the recommendation. Specified separately in image-pipeline.html; nothing here depends on it.
The signup moment Below the verdict, not above it: "Keep this and get tomorrow's". The person is holding something; the offer is to keep holding it.
04

The draft — one object, browser-owned

A guest has no row in Mongo. Their answers live in sessionStorage under one key, in one shape, and that same shape is what the decide endpoint takes and what signup replays. No guest collection, no anonymous user documents, no cleanup job. 

// web/src/features/decide/types/decide.types.ts
export interface DecideDraft {
  v: 1;                          // shape version
  startedAt: string;                // ISO, for funnel timing
  kitchenItems: string[];           // [] means "nothing"
  kitchenSkipped: boolean;          // [] + skipped ≠ [] + picked none
  mood: Mood | null;
  weight: Weight | null;
  minutes: 15 | 40 | 90 | null;
  city: string | null;
  verdict: DecideVerdict | null;  // the answer, once given
}
sessionStorage, not localStorage The tokens in session-store.ts must survive a reload, so they use localStorage. A taste draft must not outlive the tab — a shared laptop should not greet the next person with someone else's mood. Every read and write is try/caught exactly as session-store.ts does it, because storage throws outright in some private windows.

Lifecycle

  1. Created on the first tap of step 2, not on landing — a bounce writes nothing.
  2. Patched per step. Each step writes only its own slice, mirroring OnboardingService.save's $set-only-what-was-sent discipline.
  3. Sent whole to POST /api/v1/decide. The server is stateless about it.
  4. Verdict written back into the draft, so a reload of the verdict screen costs no second AI call.
  5. Replayed at signup: register → PATCH /onboarding → POST /onboarding/complete.
  6. Cleared once replay succeeds. On failure it is kept and retried — losing the answers is worse than a duplicate write.
1storage key
0new collections
0cleanup jobs
Size discipline kitchenItems is capped at 40 entries client-side and re-validated at 40 by the Zod schema, each name ≤ 80 chars — the same bounds ExtractedItemSchema already uses. A draft cannot become an upload channel, and express.json({ limit: '1mb' }) is the outer backstop.

06

How the decision is actually made

Same doctrine as DailyRundownSchema already encodes: we pick the meal, the model writes the words. The model never sees a meal we do not have and cannot invent one — so a hallucinated dish is structurally impossible, not merely unlikely.

STAGE 1 · deterministic
Filter
Published meals only. Drop anything over the minutes ceiling. Keep the weight-tag matches.
STAGE 2 · deterministic
Match
indexStock() + matchMeal() verbatim, with the draft's items adapted into stock-shaped rows.
STAGE 3 · deterministic
Rank
Score × mood weighting × weather nudge. Take the top 3.
STAGE 4 · one model call
Frame
The 3 candidates + the answers go in. One why for the winner and a framing line come out. decide.verdict prompt id.
STAGE 5 · fallback
Degrade
Model down, slow or unparseable → serve stage 3's winner with a templated why. provenance: "deterministic".

Adapting a draft into the matcher

matchMeal() takes the index that indexStock() builds from StockItemDocument[]. A guest has no stock rows — so the decide service builds the index from synthetic rows instead: 

// quantity is unknown, so it must read as "have it",
// never as 0 — indexStock() drops quantity <= 0,
// which would make every tapped item read as missing.
const rows = items.map((name) => ({
  name,
  catalogueId: resolve(name)?.id ?? null,
  quantity: 1,
  unit: null,
}));
The trap hasEnough() returns true when need.unit is null or unconvertible — which is exactly right here. A guest tapping "rice" is asserting presence, not quantity, so no ingredient should ever come back low on the anonymous path. If one does, the adapter is wrong.

Weather nudge, when a city is given

  • Hot & humid (>30°C) — down-weight heavy swallow, up-weight light and soupy.
  • Rain — up-weight soupy and pepper soup.
  • Harmattan / cool — up-weight pepper soup and hot stews.
  • Lookup fails — nudge is skipped silently. Weather is a garnish, never a dependency.

The new prompt

One addition to PROMPT_IDS, one to SYSTEM_PROMPTS, one schema in ai.contracts.ts. It inherits NIGERIAN_CONTEXT and METRICS_CONTRACT like every other prompt, so the prompt log grades it on the same axes as the rest. 

// lib/ai/prompts.ts
DECIDE_VERDICT: 'decide.verdict',

// lib/ai/ai.contracts.ts
DecideVerdictSchema = withEnvelope({
  // MUST be one of the ids we supplied.
  // A value we did not send is a rejected reply.
  chosenMealId: z.string().min(1).max(60),
  why: z.string().min(1).max(200),
  framing: z.string().max(160).nullable(),
});
Prompt shape
  • "You are choosing between three meals we already have. You may not name any other meal."
  • "Pick the one that best fits the answers. Return its id exactly as given."
  • "why is one sentence, and must reference at least one real thing they told us — an item they have, their mood, the time, or the weather."
  • "Never claim they have something not in the list."
  • "No greeting. No 'great choice'. No exclamation marks."
Validation is a rejection, not a repair A chosenMealId outside the three we sent means the reply is discarded whole and stage 5 serves the deterministic winner. Exactly the doctrine in ai.contracts.ts: "a reply that does not parse is REJECTED, never patched up."
Latency budget Stages 1–3 are in-memory over the published meal set — single-digit milliseconds. Stage 4 is the only slow part, and it is bounded: a 4-second timeout, after which stage 5 answers. The verdict screen therefore has a guaranteed ceiling and can never hang on the model. The step-5 button shows the marching indeterminate band (kj-march), never a fake percentage.
07

Changing your mind

A single take-it-or-leave-it verdict is a coin flip with extra steps. The person must be able to say "not that" and get something else — but every such path has to cost zero model calls, or the public endpoint's whole cost model collapses. That constraint is what makes this design work rather than complicate things.

A

Not this one

Rejects this dish specifically and promotes the next candidate. The rejected meal is added to an exclusion list and never comes back this session.

free · local
B

Something else

Promotes an alternate the person picked from the two shown. A lateral move inside the same shortlist, not a re-decision.

free · local
C

Change an answer

Reopens one step — usually mood or time — keeping everything else. Re-ranks the same candidate pool against the new answers.

free · local
D

Start again

Clears the draft and returns to step 1. The only path that can spend a second model call, and the only one that touches the rate limit.

1 token
Why A, B and C are free POST /api/v1/decide returns the whole ranked shortlist, not just the winner — the top 6 with their match data, plus the framing. The model call already happened; re-ranking six objects the browser is holding is arithmetic. So the three things a person is most likely to do after seeing a verdict all cost nothing, and the expensive path is the rare one.

What changes in the response

The shape from §05 grows a pool. Each entry carries its deterministic match data and the tags the local re-ranker needs, so the client can reproduce stage 3's ordering without the server.

The trap worth naming The model wrote one why, about the winner. When a promoted meal takes the top slot it must not inherit it — that sentence cites ingredients and reasons belonging to another dish, and displaying it would be a confident lie. Promoted meals show their templated line, composed from real match data, and the grape provenance chip is dropped for them.

The exclusion list

One field on the draft. It is what makes "not this" feel like being listened to rather than a reshuffle. 

// decide.types.ts — added to DecideDraft
/** Meals this person has said no to, this session. */
rejected: string[];   // meal ids, capped at 20
pool: PoolEntry[];  // the shortlist, held for free re-ranks
  • Sent back on the next real call. If the person eventually does hit "Start again", rejected travels with the request so stage 1 filters those meals out. Saying no twice to the same dish is the clearest sign we were not listening.
  • Capped at 20 and validated server-side, same bounds discipline as kitchen_items.
  • Session-scoped. It expires with the tab. A dish refused on a Tuesday should not be banned forever — and if the person signs up, the rejections are not carried over, for the same reason mood is not: it was true for one evening.

When the pool runs dry

Six rejections exhausts the shortlist. The honest move is to say so and offer the one path that can genuinely help:

"That's everything that fits." "Nothing left that matches a 40-minute solid meal with what you have. Loosen the time, or tell us one more thing that's in your kitchen."

This routes back to a step, not to a refusal — and widening the filter is exactly what will produce new candidates, so the suggestion is actionable rather than a shrug.

08

Rate limiting — the public AI endpoint

POST /api/v1/decide is unauthenticated and spends money at OpenAI. That combination is the single most abusable surface this app will have, so it gets its own named policies rather than borrowing one. Two new entries in RATE_LIMITS; the existing token bucket and middleware need no changes. 

// lib/ratelimit/limits.ts — additions only

/**
 * The anonymous decision. UNAUTHENTICATED and it spends
 * money at OpenAI — the worst pair in the system.
 *
 * Deliberately NOT AI_CALL: that policy keys by identity,
 * and on a public route byIdentity falls through to IP
 * anyway while reading as though a user were involved.
 * A separate name states that this bucket guards a
 * surface with no account behind it.
 *
 * 8 burst / hour is generous for a real person (who needs
 * one, maybe three on a fussy day) and useless to a
 * scraper.
 */
DECIDE_ANON: perWindow('decide_anon', 8, HOUR),

/**
 * The tiles. In-memory, no DB, no model — cheap enough
 * to be generous, bounded so it cannot be a DoS lever.
 */
DECIDE_OPTIONS: perWindow('decide_options', 120, MINUTE),
Why byIp is passed explicitly The default resolver is byIdentity, which returns ip:… only as a fallback. On a route that is public by design, the key must say so at the callsite — so rateLimit(RATE_LIMITS.DECIDE_ANON, byIp) is written out, exactly as app.ts does for the GLOBAL backstop.

The budget, per IP

Real person, one sitting1–3 / 8
Fussy person, re-deciding5–8 / 8
Scraperrefused at 9

Layers a request passes through

  1. trust proxy: 1 — one hop, so req.ip is the real client and not a forgeable chain.
  2. GLOBAL — 900/min per IP, the app-wide backstop in app.ts.
  3. DECIDE_ANON — 8/hour per IP, the real guard.
  4. validate(DecideSchema) — a malformed body is refused before any model call.
  5. "Something else" is local. Re-ranking spends no token at all, so the commonest repeat action costs nothing.
Refusal is already well-behaved The existing middleware sets X-RateLimit-* on every response and a real Retry-After on refusal, and app.ts already exposes those headers through CORS. The client shows "you've had a few — come back in {n} minutes, or make an account for unlimited" — which turns the limit into the signup pitch.
Known limitation, stated not hidden MemoryRateLimitStore holds buckets in process memory, so with more than one instance each enforces separately — n instances means 8n per hour. That is documented in the store itself and acceptable for a single instance. Before scaling horizontally, implement RateLimitStore against Redis; it is one new file and one line in the factory, with no callsite changes. Shared NAT is the other real case: a campus or office behind one IP shares the bucket. 8/hour is set high enough that a handful of colleagues each get an answer, and signing in moves them to their own per-user bucket.
09

Abuse beyond volume

Rate limiting stops a flood. It does not stop a single clever request — and a public endpoint that reaches a language model is a prompt-injection target by definition.

VectorWhat it looks likeWhy it does not work here
Free-model proxy Someone tries to use /decide as a general LLM: prompt text smuggled into kitchen_items. Structurally blocked. The model never sees free prose as an instruction — it receives three meal ids and a small set of enum values. Items are matched against CATALOGUE and an unresolved name is passed only as a bounded 80-char string, never as a directive. The output schema permits exactly one id, one sentence and one framing line; anything else is discarded.
Prompt injection kitchen_items: ["ignore previous instructions and …"] Even a fully compliant model can only answer with chosenMealId from our three. The worst achievable outcome is an odd why sentence, capped at 200 characters and rendered as text, never as markup. And metrics.ambiguity spikes on exactly these calls, which makes them findable in the prompt log.
Cost amplification Maximal payload every time — 40 items of 80 chars. Bounded by construction: input to the model is the candidate meals plus enums, not the raw item list, so token count per call is near-constant regardless of payload size. express.json caps the body at 1MB; Zod caps the array at 40.
IP rotation Residential proxy pool, one call each. The honest answer: rate limiting alone does not stop this. Mitigation is economic — each call yields one meal name and one sentence, which is worth less than the proxy. If it is ever observed, the escalation path is Turnstile on step 5 only (the last tap before the spend), which leaves steps 1–4 frictionless.
Scraping the catalogue Hammer /decide/options to lift the item list. Low value — it is a list of Nigerian foodstuffs, not proprietary. Bounded at 120/min, served from memory, and it is the same data any visitor sees in the UI.
Verdict forgery Hand-edit the draft in sessionStorage to fake a verdict, then claim it. Costs the attacker nothing and gains nothing: the claim endpoint writes only prefs and kitchenItems, and re-derives everything else server-side. A forged verdict buys a wrong meal suggestion for oneself.
Every anonymous call is logged like every other model call ai-log.model.ts already records prompt id, parse outcome and the self-graded metrics. Anonymous calls go in the same log with the IP hash rather than a user id — so the console's existing AI view answers "is this endpoint being abused" and "is this prompt any good" with no new tooling.

The claim sequence

1 · existing
POST /auth/register
{ email, password, name, city } — city lifted from the draft. Unchanged endpoint.
2 · existing
Tokens stored
sessionStore.set(), exactly as the current register screen does.
3 · existing
PATCH /onboarding
Sends only the keys the draft holds. Status pending is allowed here by design.
4 · existing
POST /onboarding/complete
The draft answered every question onboarding asks — so the new account skips it entirely.
5 · new
Clear & land
Draft cleared, redirect to the kept meal.
Why pending already works Onboarding is the one write surface a pending account may use — the routes list [ACTIVE, PENDING] precisely so a new account is not deadlocked out. And meals.routes.ts already allows PENDING to read a recipe and cook it. A guest who converts can cook before they verify their email. That was already true; this flow just depends on it.
Failure handling Steps 3–4 are best-effort. If PATCH /onboarding fails, the account still exists and the draft is kept, not cleared — retried on next boot. If complete returns 409 ONBOARDING_ALREADY_COMPLETED, that is treated as success: the service's own comment says the client should read it as "already done, carry on".
The alternative considered and rejected A server-side guest session — a real document, an anonymous token, a claim-by-id handshake. It buys cross-device continuity, and costs a new collection, a TTL cleanup job, a second token kind, and a new unauthenticated write endpoint that creates rows. For a flow whose entire state is four enums and a word list, the browser is the right owner. Revisit only if funnel data shows people genuinely starting on a phone and finishing on a laptop.

How we will know whether it worked

The flow is a funnel, so it must be measured as one. Every number below is derivable from the draft's startedAt plus the existing request log and AI log — no new analytics dependency.

The funnel
  • Landed → tapped start
  • Start → finished kitchen (and skip rate)
  • Kitchen → mood → weight → time
  • Time → verdict served
  • Verdict → signup (the number that matters)
Quality
  • metrics.outputConfidence per verdict
  • metrics.ambiguity — spikes flag injection and thin inputs
  • Fallback rate — stage 5 firing often means the prompt or the timeout needs work
  • "Something else" taps per verdict — high means the first pick is wrong
  • Rejections per verdict — the cleanest negative signal we get; see §07
  • Pool exhaustion rate — how often six candidates were all refused
Cost & abuse
  • Model calls per day on decide.verdict
  • 429 count on decide_anon
  • Distinct IPs vs. calls — a ratio near 1.0 over many IPs is a rotation signal
  • Cost per signup, which is the only cost number that means anything
The one decision this data should drive If verdict→signup is healthy but few people reach the verdict, the questions are too many — drop time-and-place and default it. If people reach the verdict and do not convert, the verdict is not good enough, and the fix is ranking, not copy. Those two failures look identical in a single conversion number, which is why the funnel is split at every step.

Build order

Sequenced so something real is testable at the end of each stage, and so the expensive, abusable part is never the first thing shipped.

#StageContainsDone when
1Deterministic core features/decide service: filter → match → rank. The draft-to-stock adapter. No AI, no routes. A unit test feeds a draft and gets a sane top-3, including the empty-kitchen case.
2Public endpoints GET /decide/options, POST /decide with templated why. Both new rate policies wired with byIp. Zod schema. A verdict comes back with no model involved, and the 9th call in an hour is refused with a real Retry-After.
3The flow, client side Draft store, five steps, verdict screen, and the free recompute controls (§07) — pool, exclusions, local re-rank. Behind the feature flag; old landing still owns /. The whole flow is walkable end to end at /decide on a phone viewport.
4The model call decide.verdict prompt, DecideVerdictSchema, the 4s timeout and stage-5 fallback. Killing the provider still returns a verdict, marked deterministic.
5Carry-over The claim sequence, all three entry points, retry-on-failure. A guest converts from each of A, B and C and lands on their meal with onboarding already complete.
6Switch & watch Flag flips / to the flow; old landing to /why. Funnel and cost dashboards. Funnel is visible per step, and the flag can revert without a deploy.
7Imagery & stories
separate doc
 Meal photography as a background job, then the verdict as a swipeable story set. Fully specified in image-pipeline.html. Ships only after 1–6 work without it; with no images configured the flow is unchanged.
Why the AI comes fourth Stages 1–3 deliver a complete, shippable product with no model cost and no public AI surface. If stage 4 were first, every problem in ranking, in the funnel and in the rate limiting would surface as "the AI is wrong". Building the deterministic answer first also guarantees the fallback in stage 5 is real code that has been exercised, not a branch written once and never run.
