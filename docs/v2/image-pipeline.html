Recipe Imagery

A recipe holds many images, one marked primary. An operator adds them from the console — either by uploading a real photograph, or by clicking Generate and letting a background job produce one. Nothing reaches a cook until a person has looked at it and said yes.

Operator-driven, not automatic Many images per recipe One primary Generation is a queued job Upload and generate, same pipe
01

What changed, and why it is better

An earlier draft of this document specified a catalogue-wide sweep: enqueue every published recipe, generate, auto-check, park for review. That design was wrong in a way worth recording, because the reason generalises.

The sweep model

Spend first, look later

  • It spends money before anyone has judged the prompt. 340 generations at prompt v1 produces 340 images at v1 quality — and the first fifty are what teach you the prompt is wrong.
  • It cannot use a real photograph. If someone has actually cooked ewa agoyin and photographed it, that image is better than anything generated, and a generate-only pipeline has nowhere to put it.
  • One image per recipe. No second attempt kept alongside the first, no seasonal variant, no choosing between two good options.
  • A daily cap is a crude control. It bounds spend but says nothing about whether the spend was useful.
The console model

Look first, spend per click

  • Every generation is a deliberate act by a person looking at that recipe. Spend is bounded by intent, which is a better control than a cap.
  • Upload and generate land in the same place. A real photograph is just an image whose source is upload — the rest of the system does not care how it arrived.
  • Many images per recipe, one primary. Keep two attempts, promote the better one, swap later without regenerating.
  • The prompt improves through use. An operator regenerates with an edited prompt, sees the result in a minute, and the good wording gets saved.
The backfill still works Bulk-selecting rows in the recipes list and clicking Generate enqueues one job each. Same handler, same queue — the difference is a person chose the batch.
What is unchanged from the earlier draft Generation is still a queued background job, never on a request path — an image model takes 5–20 seconds and a console request must not hold a connection for it. Images are still public, immutable objects served without a signature. A human still approves before anything goes live. Those three were right; only the trigger was wrong.
02

The shape

Two ways in, one pipe out. Whether the bytes came from an operator's disk or from OpenAI, everything downstream — storage, derivatives, review, serving — is identical.

IN · A
Upload
Operator picks a file. Presign → PUT → confirm, the flow features/files already implements.
IN · B
Generate
Operator clicks. A recipe-image job is enqueued and the console follows its progress.
THEN
Derivatives
hero / card / thumb / blur, written to public/recipes/…. Identical for both sources.
THEN
Review
Lands as review. An operator publishes it, or rejects it with a reason.
THEN
Primary
Exactly one published image per recipe is primary. It is what every single-image surface uses.

Two decisions carried forward

1 · Generation is never on the request path. The console click enqueues and returns immediately; progress arrives over the existing job SSE stream, with polling as the fallback. lib/jobs already gives leases, retries, setProgress and cooperative cancellation — a generation job is an ordinary citizen of a queue that already runs extraction and insights.

2 · Recipe images are public objects, not user files. files.presenter.ts presigns per response because a shelf photo is private and a stored URL would expire. A recipe image is the opposite — public, immutable, shared. Presigning would defeat CDN caching and make a three-card carousel three signatures.

The one new env var S3_PUBLIC_BASE_URL, defaulting to ''. Empty means no public serving is configured, and the presenter returns null so every surface falls back to the drawn heroIcon — the same graceful degradation isStorageConfigured() already does.
Why many images, not one
  • A generated image and a real one can coexist. Use the photograph as primary and keep the generated one as a fallback, or the reverse.
  • Two attempts are worth keeping. Regenerating today should not destroy yesterday's acceptable result — that is how you end up with nothing.
  • The carousel wants more than one. §10 shows the verdict as three story cards; a recipe with two good images can vary what it shows.
  • Promotion is free. Changing which image is primary is one field write, not a regeneration.
And a cap

Eight images per recipe. Enough for real choice, bounded so a stuck regenerate loop cannot fill the bucket. Enforced in the service, not just the UI.

03

Data model

An array of sub-documents on the meal, plus one pointer. Images are always read with their recipe and never queried independently, so a separate collection would add a join to the hottest read in the product for no benefit. 

// features/meals/meals.model.ts

export interface RecipeImage {
  _id: string;
  /** The R2 folder key. NEVER a URL — same rule as files. */
  key: string;
  /** How it got here. Drives the provenance mark shown to cooks. */
  source: 'upload' | 'generated';
  status: 'pending' | 'review'
        | 'published' | 'rejected';

  /** Tiny base64 placeholder, ~400B. Cheaper inline than a request. */
  blurData: string | null;
  width: number | null;
  height: number | null;
  bytes: number | null;

  // ── generated only ──────────────────────────────
  /** Exactly what we sent. A good image is reproducible,
   *  a bad one diagnosable. */
  prompt: string | null;
  model: string | null;
  promptVersion: number | null;
  /** The vision pass's self-grade, for the review sort. */
  checkConfidence: number | null;
  checkReason: string | null;
  /** The job that made it, so its log is reachable. */
  jobId: string | null;

  // ── audit ───────────────────────────────────────
  addedBy: string;              // admin user id
  reviewedBy: string | null;
  reviewedAt: Date | null;
  rejectionReason: string | null;
  createdAt: Date;
}

// on MealAttributes:
images: RecipeImage[];        // capped at 8
/** Which one is THE image. Must point at a
 *  published entry in `images`, or be null. */
primaryImageId: string | null;

The primary pointer, and its invariant

A pointer rather than an isPrimary boolean on each image. A boolean permits two primaries and zero primaries, and both are states someone has to write code to handle. A single nullable pointer can only be valid or null.

One invariant, enforced in the service primaryImageId is either null or the id of an image in this recipe whose status is published. Three consequences:
  • Publishing the first image auto-sets it primary — a published image with no primary would be invisible everywhere.
  • Rejecting or deleting the primary promotes the next published image, or nulls the pointer if none remain.
  • Setting primary to an unpublished image is refused, not silently corrected.

Lifecycle

pending→ review→ published
review→ rejected kept, with a reason
  • pending — a row exists, bytes may not have landed yet. Exactly the semantics FILE_STATUSES.PENDING already has, and for the same reason: the server never observes a direct-to-R2 PUT.
  • rejected images are kept, not deleted. The rejection reason is the raw material for the per-dish hint map, and a deleted row takes its own lesson with it. An operator can hard-delete separately.
  • No failed state. A generation that errors fails the job, and the queue already models that. No image row is created for bytes that never existed.

05

Manual upload

The path that needs the least new code, because features/files already implements presign → PUT → confirm, and its rule that bytes never pass through the API applies here exactly as written.

  1. Operator picks a file. The console validates type (image/jpeg, image/png, image/webp) and size (≤ 10MB) before asking for anything.
  2. POST /admin/recipes/:mealId/images/upload-url returns a presigned PUT against a public/recipes/… key, and creates the image row as pending.
  3. Browser PUTs straight to R2. No bytes through our server — the existing rule, honoured.
  4. POST …/images/:imageId/confirm calls objectExists(), and only then moves the row to review. This is what stops a row claiming a file that was never uploaded.
  5. A recipe-image-derive job generates the card, thumb and blur from the uploaded original.
  6. Operator publishes it. Same review step as a generated image.
Why an upload still goes through review It looks like a formality when the operator just chose the file. It is not: the derive job must finish before the image is usable, and review is the state that means "bytes confirmed, derivatives done, not yet live". Skipping it would mean publishing an image whose thumbnail does not exist yet.

The one genuinely new storage primitive

Generation produces bytes inside the worker. There is no client to presign for, so a server-side put is the only route. 

// lib/storage/s3.ts — a new, narrowly-scoped export

/**
 * Writes bytes we generated or derived ourselves.
 *
 * The presign rule above governs CLIENT uploads:
 * proxying a person's file through the server pays
 * for the bandwidth twice. Bytes that originate in a
 * worker have no client to presign for, so this is
 * the only route — and it runs off the request path,
 * where the bandwidth is not contended.
 *
 * `public/` objects are served WITHOUT a signature,
 * so this must never be handed user content.
 */
export async function putPublicObject(input: {
  key: string;          // MUST start with `public/`
  body: Uint8Array;
  contentType: string;
  cacheSeconds?: number;  // default one year
}): Promise<void>
The guard that must exist putPublicObject throws unless the key starts with public/. Without it, one careless call publishes a user's shelf photo to an unauthenticated URL. The prefix is the security boundary, so it is asserted in code and not left to convention.
06

Generate

One click enqueues one job. The console follows it over the SSE stream that jobs.sse.ts already serves, falling back to polling GET /jobs/:id — the pattern the extraction flow already uses, so there is nothing new to build on the client but a panel.

1 · deterministic
Compose
Build the prompt from the recipe's own fields, plus any per-dish hint. No model call. Operator may have edited it.
2 · image model
Generate
One call, 1024². The queue's own attempt logic retries a transport failure up to 3×.
3 · vision model
Self-check
"Is this the dish we asked for?" Cheap. A clear miss is discarded before it costs storage or an operator's attention.
4 · storage
Store
Derivatives written to public/recipes/<slug>-<nonce>/. Row created at review.
5 · person
Decide
Publish, or reject with a reason that feeds the hint map.

The handler, in the house style

Mirrors insights.jobs.ts: narrow payload, setProgress between steps, isCancelled checked, a skip result rather than a throw when there is nothing useful to do. 

// features/meals/meals.jobs.ts
export const RECIPE_IMAGE_JOB = 'recipe-image';

async function runRecipeImage(payload, ctx: JobContext) {
  const { mealId, promptOverride, actorId } =
    payload as RecipeImagePayload;

  const meal = await MealModel.findById(mealId).exec();
  if (meal === null)
    return { skipped: true, reason: 'recipe is gone' };

  // The cap is enforced here too, not only in the UI —
  // a queued job can outlive the state it was queued in.
  if (meal.images.length >= MAX_IMAGES)
    return { skipped: true, reason: 'at the image cap' };

  await ctx.setProgress(0.1, 'Writing the shot');
  const prompt = promptOverride ?? composeImagePrompt(meal);

  if (await ctx.isCancelled()) return { cancelled: true };

  await ctx.setProgress(0.3, 'Cooking the picture');
  const img = await aiService.image({ prompt,
                                     ownerId: actorId });
  if (!img.ok) throw new Error(img.error); // queue retries

  await ctx.setProgress(0.6, 'Checking we got the dish');
  const check = await verifyDish(img.bytes, meal);
  // A confident miss never reaches storage or a person.
  if (!check.isDish && check.confidence > 0.8)
    return { rejected: true, reason: check.reason };

  await ctx.setProgress(0.85, 'Putting it away');
  const key = await storeDerivatives(meal.slug, img.bytes);

  await appendImage(meal, { key, source: 'generated',
    status: 'review', prompt, check, addedBy: actorId });

  await ctx.setProgress(1, 'Ready for review');
  return { key, confidence: check.confidence };
}

Editing the prompt before regenerating

The highest-leverage control in the whole feature. When a dish comes back as the wrong food, the fix is almost always one clause — and an operator who can add it and see the result in a minute will fix it, where one who must file a ticket will not.

  • The composed prompt is shown, editable, pre-filled from composeImagePrompt(meal).
  • An override is stored on the image it produced, so a good result is reproducible.
  • "Save this as the hint for this dish" writes the edit into the per-dish hint map, so the next regeneration starts from the better wording.
This is how the prompt gets good Image models get Nigerian food wrong in confident, repeatable ways — jollof as paella, egusi as guacamole, amala as chocolate mousse. Each entry in the hint map is written the first time an operator hits that specific confusion. The catalogue improves through use rather than through a rewrite.

The vision pre-check

A cheap vision call on the bytes we just made, using the existing OPENAI_VISION_MODEL and the same envelope discipline as every other contract. New prompt id: image.verify. 

RecipeImageVerdictSchema = withEnvelope({
  isDish: z.boolean(),
  looksHomemade: z.boolean(),
  hasForbidden: z.boolean(),
  confidence: z.number().min(0).max(1),
  reason: z.string().max(200),
});

It exists to make the human pass short, not to replace it. It costs a small fraction of the generation it validates, so discarding a clear miss before storage is strictly cheaper than storing it and having a person find it later. Borderline cases go to review with their confidence recorded, lowest first.

07

The prompt

Composed from the recipe's own fields, so 340 prompts are one function rather than 340 strings. The hard part is not describing the food — it is stopping the model producing a glossy restaurant plate when the product is about home cooking. 

// features/meals/meals.image-prompt.ts
// Bumped whenever the wording changes, so a sweep can
// find every image made by an older version.
export const IMAGE_PROMPT_VERSION = 1;

export function composeImagePrompt(meal: MealDocument) {
  const key = meal.ingredients
    .filter((i) => !i.optional)
    .slice(0, 5)
    .map((i) => i.name);

  return [
    `A photograph of ${meal.name}, a Nigerian dish.`,
    `Made with ${key.join(', ')}.`,
    SHOT,               // framing, light, surface
    AUTHENTIC,          // the anti-restaurant clause
    HINTS[meal.slug] ?? '',  // per-dish correction
    NEGATIVE,           // what must not appear
  ].filter(Boolean).join('\n\n');
}
The clause that does the most work "Served in a real Nigerian home: an ordinary plate or enamel bowl, no garnish that would not be there, no styling, no restaurant plating, no microgreens, no drizzle." Without it every dish arrives fine-dining-plated and the product reads as aspirational rather than useful.

The full wording, the hint map and the verification prompt live in recipe-photography.md beside this file — reviewable as copy rather than buried in a service, and readable by an operator wondering what was sent.

The per-dish hint map

Ordinary data, small, and the part that improves through use. Each entry is written the first time an operator rejects an image for that confusion.

DishCorrection
Jollof riceOrange-red from tomato and pepper — not yellow, not paella, not biryani.
EgusiCoarse pale-green melon-seed stew, lumpy — not guacamole, not pesto.
AmalaSmooth very dark brown swallow, matte — not chocolate, not mousse.
OgbonoDark, visibly slimy drawn soup. The texture is correct and must show.

Twelve entries at the time of writing. It is expected to grow, and growth is the feature working rather than a sign it is not.

Provenance is not optional A generated image carries a visible Illustration mark in grape wherever it appears at hero size — it is a generated picture of food, not a photograph of the dish this person will produce. An uploaded photograph carries no such mark, because it is a real photograph. This is exactly why source is stored per image, and it is the same rule the AI-written why on the verdict already follows.

  • Immutable, so cache forever. Cache-Control: public, max-age=31536000, immutable — the nonce means a new image is a new URL, so nothing ever needs purging.
  • Only the folder key is stored. Derivative names are a convention, so one string yields all four URLs.
  • Blur lives in Mongo, not R2 — at ~400 bytes it is cheaper inline than as a request.

  1. No S3_PUBLIC_BASE_URL → image: null everywhere, and every surface falls back to the drawn heroIcon.
  2. No published image → same null, same fallback.
  3. Image 404s in the browser → onerror swaps in the koboyo glyph. A dead link never shows a broken-image icon.

The test that matters With S3_PUBLIC_BASE_URL='' the app must look and behave exactly as it does today. Imagery is an enhancement layer, and it is only safe to ship as one if that is verified rather than assumed.

Cost

The console model changes the cost shape, not just the amount: spend is now proportional to operator clicks rather than to catalogue size, and a click is a person deciding an image is worth having.

What bounds the spend

ControlBound
A person clicksThe real control. No background process spends money on its own.
IMAGE_GENERATE60/hour. Stops a stuck console retry loop, not a human.
8 images per recipeEnforced in the service. A regenerate loop cannot run away.
Vision pre-checkA confident miss is discarded, so a bad generation does not also cost storage and attention.
Bulk confirmA bulk generate states the call count and needs a confirm before enqueueing.
Still bounded by catalogue, not by traffic 340 images cost the same whether 10 or 10 million people see them. R2 has no egress charge, which is the reason it beats S3 for this. Serving is effectively free; only making them costs.

Still never on the request path

Worth restating, because it is the constraint that shaped both this design and the one it replaced: generating an image when a cook asks for a verdict would be a money pump on a public, unauthenticated endpoint.

  • Images cost roughly 10–40× a text call. DECIDE_ANON at 8/hour bounds the text path to something survivable; at that multiple, the same bucket does not.
  • The 4-second verdict ceiling would become impossible to hold against a 5–20 second generation.
  • The same popular meal would be regenerated per visitor, paying repeatedly for an identical result.

So the decide endpoint's cost model is unchanged by this feature. It reads a URL that already exists, or it renders a drawn glyph.

10

What imagery unlocks

With real images, the verdict stops being a card and becomes a swipeable set of three — the format people already know from Instagram and WhatsApp status. The screens are drawn in design.html §07; what follows is only what this pipeline owes them.

Needs

Published images, primary first

The carousel asks for images[], not just the primary. A recipe with two published images can vary what it shows; one with none falls back to the drawn glyph on a tinted plate and the carousel still works.

Needs

The blur, always

A carousel is three heroes. Without an inline placeholder the first swipe is three empty rectangles on a slow connection, which is worse than no imagery at all.

Needs

The source field

The grape Illustration mark appears on generated images and not on photographs. The card cannot make that distinction unless the API states it per image.

The carousel must not become a list Three cards, hard maximum, and card one is still the recommendation — larger, first, and the only one whose "why" is fully model-written. A carousel of equals is a menu, and a menu is the problem the person arrived with.
11

Build order

Imagery is an enhancement layer, so it ships strictly after the decide flow works without it. Note that upload comes before generate — it is cheaper, simpler, and it proves the whole pipe with no model involved.

#StageContainsDone when
1Storage primitive putPublicObject with the public/ prefix guard. S3_PUBLIC_BASE_URL. URL composition in the presenter. A hand-placed test object serves over a public URL with a one-year cache header.
2Model & the null path RecipeImage[], primaryImageId and its invariant, presenter returning image: null. The whole app behaves identically with no images present. The safety net for everything after.
3Upload The three upload routes, the derive job, the console Images panel with publish / reject / make-primary. An operator adds a real photograph and it appears on the verdict. No model involved yet.
4Generate recipe-image job, prompt composer, hint map, vision pre-check, the console's progress panel over SSE. One click produces a reviewable image, and killing the provider fails the job cleanly without a phantom row.
5Prompt editing Editable prompt on regenerate, override stored per image, "save as hint for this dish". An operator fixes a wrong-dish result themselves and the fix persists.
6Backfill Image-count column, gap filters, bulk select → generate with a confirm. The catalogue has imagery, and gaps are visible while scanning the list.
7Stories The carousel on the verdict, hook line, pitch line. Swiping three cards works on a phone — and still works with images absent.
Why stage 2 is the one not to skip Building the null-image path before any image exists is what makes this feature safe to ship incrementally. Done in the other order, "no image yet" becomes a bug to chase in six surfaces instead of the designed default in one.
Why upload comes before generate Stage 3 exercises storage, derivatives, review, primary promotion and every console control — with no model, no prompt and no spend. If generation were first, every problem in that chain would present as "the AI is wrong". It also means the fallback for a dish generation keeps failing on is real code that has been used.
