02

The isolation rule

You were explicit: this must not touch or break the current decide flow. That is a structural requirement, not a promise to be careful, so it is written as rules a reviewer can check.

Hard boundaries

  • New feature folder. features/ask/ on both sides. No file under features/decide/screen/ is edited except the four step splits in stage 0, which are pure refactors with the v1 flow's own tests holding them.
  • Same endpoint, unchanged. POST /decide keeps its exact payload and response. Chat is a different way to fill that payload, not a different payload.
  • Same draft store. decideDraft v1 shape untouched. The transcript is rendered from the draft, never stored beside it.
  • New routes only. /ask and the two new API paths. / and /decide behave exactly as today.
  • Its own rate-limit policies. A chat session must never spend the tap flow's DECIDE_ANON budget.
Review gate: a diff that modifies decide.service.ts, decide.ranker.ts or decide-screen.tsx has broken the isolation rule and should be rejected.

Zero shared components

The v1 step components are not reused, adapted or split. Ask gets its own, written for a dock. Nothing under features/decide/screen/ is edited at all.

v1 stepsUntouched. Not imported, not refactored.
∥
ask/dock/*New components, built for this surface.
This is the stronger choice and it was the right correction. Forcing a h-dvh component with its own header and footer into a dock would have produced a compromise that served neither: v1 constrained by chat's needs, chat constrained by v1's layout. Separate components mean the isolation rule has no exception — the review gate becomes "does this diff touch features/decide/", full stop.
What IS shared, safely: the catalogue payload from /decide/options, the DecideDraft type, decide-rerank, and the verdict deck mounted whole. Data and leaf modules, never layout.

Every step accepts three inputs: tap a tile, type a sentence, or record a voice note. Taps stay primary and are always the fastest path; the composer sits under the tiles, visually secondary. If we ever ship a step where typing is the only way to answer, we have made the product slower.

Scroll back to change an answer

Every answer stays on screen as a tappable bubble. Tapping one re-opens that question in the dock; answering appends a correction rather than rewriting history, so the thread stays a true record.

  • Later answers are kept, not cleared — changing mood should not make somebody re-enter their kitchen.
  • The verdict IS cleared (verdict: null). A stale verdict behind the stage guard bounces straight back to it — the exact bug hit while building remix.
  • patch() already takes a Partial<DecideDraft> and merges, so no reducer change is needed.

Optimistic send

A tap or a send paints the cook bubble immediately at full opacity, with a pending flag driving only a small clock glyph in the corner.

  • Bubble enters with a 180ms rise-and-fade (translateY(6px) → 0), never a scale-in.
  • Pot's typing indicator appears only when a request is genuinely in flight. Faking thought to seem clever is the one thing here that would damage trust.
  • On failure the bubble gets a critical left edge and an inline Retry — it is never removed, because a message that vanishes reads as data loss.
  • prefers-reduced-motion drops every transition to an opacity swap.

The bottom panel

Two heights, one component

StateHeightTrigger
DockedFixed per stageDefault. Tiles + composer.
Expanded86 dvh mobile · modal desktopTap the search input.

Animation

  • 240ms, cubic-bezier(.32,.72,0,1) — the iOS sheet curve; it decelerates hard so the panel feels caught rather than stopped.
  • Animate transform and height only. Never animate a top offset; it thrashes layout on every frame.
  • Scrim fades 0 → 0.55 over the same curve.
  • Drag-to-dismiss past 40% of travel, with velocity carry.
  • inert on the thread while expanded, focus trapped in the panel, Escape closes.
The classic mobile chat bug: a dock that changes height as the keyboard opens makes the thread jump. Dock height is fixed per stage and never animates except on the deliberate expand. Use visualViewport for keyboard inset, not resize.

Contents when expanded

  • Popular group first, then the other 26 — exactly the order /decide/options already returns.
  • Selected items stay pinned at the top as chips, so a long scroll never hides what you picked.
  • Search filters across aliases, so "atarodo" finds scotch bonnet — the catalogue already carries them.
  • Footer: Use n items, which collapses the panel and posts one cook bubble.

Why one bubble, not one per tap

Twelve taps must not produce twelve bubbles. The kitchen answer is a single cook bubble that updates in place while the panel is open, and commits on close.

No new endpoint. The panel reads the cached /decide/options payload the app already fetches on landing. Opening it costs zero requests.

Voice

The decide moment happens with hands occupied, which is the real argument for voice. The transcription half is already built — this is mostly the recorder and the permission path.

The path

Tap micgetUserMedia. Permission prompt is the browser's.
→
RecordMediaRecorder → opus. Full-screen modal, live wave.
→
ReviewPlay · delete · send. Nothing uploaded yet.
→
StoragePresigned PUT, browser direct. Never through our server.
→
JobTranscribe then parse, off the request path
→
StreamRaw text first, chips after

Recorder rules

  • 30s hard cap, with the counter turning caution at 25s.
  • Auto-stop after 2.5s of silence, measured on an AnalyserNode RMS — not a fixed timer.
  • The wave is real amplitude from that same analyser. A fake animation that moves while the room is silent is a lie the user can hear.
  • Denied permission is a one-time inline note, never a repeated prompt, and the composer stays usable.

Upload

  • Direct to storage on a presigned PUT. Audio never passes through the API, so a 30s clip on a bad connection cannot occupy a node process.
  • Key ask/<session>/<ulid>.webm, 1MB cap enforced in the signature (30s opus ≈ 60KB, so this is generous).
  • Deleted right after transcription, success or failure. A 24h lifecycle rule sweeps anything the job never reached.
  • Own rate limit: ASK_UPLOAD, 20/hour anonymous.
  • Content type pinned in the presign, so the ticket cannot be reused for something else.

Provider pattern

AiProvider.transcribe() already exists. Add a thin TranscriptionProvider registry so the model is selectable independently of the text model.

  • openai-whisper — today's implementation.
  • mock — exists, returns fixed text for tests.
  • Future (Deepgram, Groq) drop in behind the same interface.
  • Selected by env, overridable per call for A/B.
  • Every call already lands in ai_logs with duration and provider.
07

Free text and voice → answer JSON

One prompt, one envelope, one shape

Both typing and voice converge on the same step: a sentence in, a partial DecideDraft out. The model never picks a meal — it only fills answers the deterministic ranker then consumes, which is the same division of labour the v1 flow uses.

Input

"rice, one tomato, I'm
exhausted, 20 minutes"

Output, enveloped

{
  "kitchen_items": ["Rice","Tomatoes"],
  "mood": "tired",
  "minutes": 20,
  "weight": null,
  "confidence": 0.86,
  "unmatched": ["one"],
  "notes": "no pepper, cooking for
            two, wants something
            light on the stomach"
}
notes is the point of speaking. See below.

Rules

  • Catalogue-constrained. Items are resolved against the 417-item catalogue with aliases; anything unresolved goes to unmatched and is shown, never silently dropped.
  • Nulls are honest. A field the sentence did not cover stays null and that question is still asked. Guessing weight from "I'm tired" is exactly the invention that makes a recommender feel wrong.
  • Always confirmable. The fill renders as editable chips with a "Not quite? Fix it" affordance. A parse is a proposal, not a decision.
  • Confidence is recorded, not displayed. It drives the dashboard and the kill decision, not the UI.
  • Below 0.5, we do not fill — we ask the question normally and log the miss.
Grape, not sky. Anything the model filled carries the grape provenance mark, the same rule the verdict already follows. A machine-made guess must never be dressed as a tap the user made.
Kill criterion, agreed in advance: if parse accuracy on the chip set sits below 85%, the correction tax exceeds the taps saved and free-text entry should be switched off at the flag. The dashboard in §12 exists to answer exactly this.

Nothing a person said is thrown away

Somebody speaking for twenty seconds says far more than four answers' worth. "I have rice, no pepper at all, cooking for my sister who hates fish, maybe twenty minutes" contains two constraints that no tile can express. Dropping them because they do not map to a field is the fastest way to make the feature feel like a worse version of tapping.

What is carried

  • The raw transcript, verbatim, for every voice turn.
  • The raw typed text, verbatim, for every text turn.
  • Both accumulate on the session across turns, so a constraint stated at step one still applies at step four.
  • notes is the model's distillation of the leftovers — the part that is not an answer.

Where it goes

  • Appended to the decide.verdict prompt as "what they also said".
  • It steers the framing sentence and the choice between near-equal candidates.
  • It never overrides the ranker. Deterministic matching still decides what is cookable; notes only inform the sentence and the tie-break.
  • Carried into ask_sessions so a session detail view shows exactly what was said.

Seen on the UI

  • The cook bubble shows the full transcript, not a four-field summary. People need to see that we heard them.
  • Under it, a grape "Also noted" chip row: no pepper, for two.
  • Each chip is dismissible — a misheard constraint must be removable without re-recording.
  • The verdict card shows which note it honoured, when one applied.
This changes the privacy stance, and it must be stated. §11 says transcripts are never recorded. Carrying notes into ask_sessions means a guest's spoken words are stored against an anonymous session row. The limits: no identity is attached, rows expire on a 30-day TTL, the raw audio is still deleted immediately after transcription, and the console detail view is admin-only. Analytics events still carry lengths and counts only — never the text.

Verdict handoff and bookmarking

Chat summarises. The deck decides.

You were clear that the last step must be the v1 interface. So the chat does not try to render a verdict — it posts a summary bubble and a button that mounts verdict-stories.tsx unchanged.

  • Summary: count, the leader, its time, and whether everything is in the kitchen.
  • View suggestions opens the existing swipe deck as a full-screen layer.
  • Swipe, Cook this, Not feeling it, Chowdeck offers and the end slide all work because it is the same component.
  • Closing the deck returns to the thread with the summary still in place.
  • "Not feeling it" re-ranks locally over the held pool — zero model calls, exactly as today.
This is the cheapest part of the plan and the highest-fidelity: no new verdict UI exists to drift from the one that already works.

Bookmark for everyone

The save affordance is visible to every user, signed in or not. Hiding it from guests hides the reason to make an account.

WhoWhat happens
Signed inPOST /meals/:id/favourite, optimistic fill, done.
GuestSheet: "Save this for later — make a free account and it is here tomorrow." Registers in place, then the save completes automatically.
The intended meal is held through signup and saved on success, so the tap is never lost. This reuses the existing carryOverDraft stance: the account is created, then the pending intent is replayed.
Distinct from the step-3 invite. That one still fires at most once per session and is unaffected. This is a consequence of an action, not an interruption, so it is exempt from the "never twice" rule — but it must never appear unprompted.

You asked for fast, low-latency, few round trips. The honest headline: most steps should make no network call at all.

Nothing blocks on a model

Every AI step is a job, and every client follows it on a stream. A request that waits on Whisper is a request that holds a connection for four seconds and dies to any proxy timeout — so no endpoint here does that. The pattern is the one extraction.jobs.ts already uses for photo and receipt reading.

1 · TicketPOST /ask/upload-url → presigned PUT. ~20ms, no body.
→
2 · Direct PUTBrowser → storage. Audio never touches our server.
→
3 · TurnPOST /ask/turn with the key. Returns turn_id immediately.
→
4 · JobTranscribe → parse. Off the request path entirely.
→
5 · StreamGET /ask/turn/:id/stream reports each phase.

Stream events

EventPayload

Every one of these is also readable from GET /ask/turn/:id. A client that cannot hold a stream polls and loses only immediacy — the rule jobs.sse.ts already states and enforces.

Guests have no owner id

The sharpest problem these changes create. filesService.requestUpload() takes an ownerId, JobModel.ownerId is required, and every /jobs route is behind authenticate. Ask must work signed out, so none of that fits as-is.

  • An ask_sessions row is the identity. Created on first turn, id is an unguessable ULID held in sessionStorage. It plays the part ownerId plays elsewhere.
  • Own routes, not /jobs. /ask/turn/:id/stream authorises on the session id, so the authenticated jobs API keeps its guarantees untouched.
  • Own key prefix. ask/<session>/<ulid>.webm, written with a storage helper that takes a session rather than an owner.
  • Audio is deleted after transcription, success or failure. A 24h lifecycle rule on the prefix is the backstop for anything the job never reached.
  • Signed in, the session carries ownerId too, so history still attaches.
A session id in sessionStorage is a bearer token for that conversation. It is unguessable and short-lived, but it is the reason the stream route must scope every read to the session, never to a bare turn id.

SSE, reusing the jobs pattern

  • 25s heartbeat, 15min cap — copied from jobs.sse.ts, which already solved proxies closing idle connections.
  • Every stream is optional. The same answer is readable from a plain POST, so a client that cannot hold a connection loses immediacy and nothing else. This is the existing rule and it is a good one.
  • Streamed: the parse fill and the verdict's why sentence.
  • Not streamed: anything structural. Ranking is deterministic and instant; streaming it would be theatre.

Database round trips

  • Zero for anonymous chat. The transcript lives in sessionStorage; nothing is written per message.
  • Published meals are already loaded once per decide call — no change.
  • Analytics writes are fire-and-forget, never awaited on a request path.
  • Signed-in: one decide_history insert at verdict, as today.
A whole anonymous conversation up to the verdict costs one database read and one model call — the same as the tap flow.

Flags

Four new flags, each switching off one layer independently. All default on, as you asked — which is a deliberate departure from how decide_invite and the tour behave, and worth stating plainly.

FlagOnOff
ask_chat The Ask KinniJije button appears and /ask works. Button hidden, route redirects to /decide. The tap flow is untouched either way.
ask_voice The mic appears and voice notes can be sent. Mic hidden. Typing and tapping still work.
ask_free_text The composer accepts a sentence and parses it. Composer hidden. The flow becomes tap-only, which is still a complete flow.
ask_streaming Parse and framing stream over SSE. Same answers arrive as one response. A performance switch, not a feature one — the escape hatch if SSE misbehaves behind a proxy.
Default-on means fail-open. These are deliberately not in FAIL_CLOSED_FLAGS: a failed flag read leaves the feature on. That is right for a product feature and wrong for anything that acts on a person without asking — which is why analytics and the tour fail closed and these do not.
Each flag needs a whenOn and a whenOff sentence written about users, matching the console convention — the admin settings screen shows both and marks the live one.

The dashboard

A new /admin/ask page, built from the same parts as the redesigned main dashboard — attention band first, then four figures, then the detail.

The four figures

  • Sessions, split ask versus tap — the "which flow are people using" number.
  • Median time-to-verdict, both flows side by side. This is the gate. If chat is slower, it does not roll out however good it feels.
  • Input mix — tap / text / voice as a proportion bar.
  • Parse accuracy, as accepted ÷ (accepted + corrected).

Alerts, derived not collected

  • Parse accuracy below 85% → critical, naming the flag to switch.
  • Mic denial above 40% → caution; voice is dead at the permission step.
  • Transcription p95 above 5s → caution, named by provider.
  • Chat time-to-verdict more than 20% above tap → critical.

Panels

  • Funnel by step, ask versus tap, so the drop-off difference is visible rather than inferred.
  • Input method per step — where people actually choose to talk.
  • Transcription by provider: calls, p50/p95, failure rate, cost. The table that justifies the registry.
  • Parse quality: confidence distribution, most-corrected field, top unmatched phrases.
  • Voice funnel: mic clicked → granted → recorded → sent → transcribed → parsed → accepted. Six places to lose someone, each worth seeing.
  • Recent sessions, clickable to a detail view, matching the decide dashboard.
Server-side truth for the two numbers that decide the feature's fate — time-to-verdict and parse accuracy — comes from a new ask_sessions collection rather than the browser, because an ad blocker must not be able to hide a regression.
12b

Motion

The thing that will make this feel expensive. Every value below is specified so it can be built and reviewed rather than improvised — and all of it collapses to an opacity swap under prefers-reduced-motion.

The thread

  • Bubble enter — 220ms, cubic-bezier(.22,1,.36,1). Rises 10px, fades in, and scales .96 → 1 from its own anchored corner so it grows out of its side rather than floating in.
  • Stagger — when the pot posts a reaction and a question together, the second is delayed 90ms. Simultaneous arrival reads as a dump; 90ms reads as a thought.
  • Typing dots — three dots, 1.2s loop, 160ms phase offset, translating 2px. Only while a request is genuinely in flight.
  • Scroll — scrollIntoView({behavior:'smooth', block:'end'}) on the newest pot message, not the raw bottom, so the question stays in view rather than the dock.

The dock

  • Step change — outgoing tiles fade and drop 8px over 140ms; incoming rise 8px over 200ms with a 35ms per-tile stagger across the grid. The staircase is the whole effect.
  • Tile select — 120ms press to scale(.95), release overshoots to 1.03 then settles. Drop edge snaps on instantly; a shadow that fades in reads as lag.
  • Panel expand — 240ms cubic-bezier(.32,.72,0,1) on transform and height only, scrim fading 0 → .55 on the same curve. Drag-to-dismiss past 40% with velocity carry.
  • Chip commit — a selected ingredient flies from its tile to the cook bubble on a 300ms arc using FLIP. Expensive-feeling, cheap to build, and it explains where the pick went.

Voice and verdict

  • Mic open — the modal scales .92 → 1 over 260ms while the scrim fades; the mic glyph pulses a 2px sky ring at 1.4s.
  • Waveform — 24 bars driven by real AnalyserNode RMS at 60fps, each eased toward its target so it breathes rather than jitters. Silence settles to a flat line, which is how you can see it has stopped hearing you.
  • Transcript arrival — words fade in 3 at a time as the stream delivers them, 40ms apart. This is the payoff of streaming the raw text rather than waiting for the parse.
  • Summary bubble — grape border draws itself clockwise over 400ms (stroke-dashoffset), then the button fades up. The provenance mark earns a moment.
  • Deck open — the summary card scales up into the full-screen deck via View Transitions where supported, cross-fade where not.
Two rules that override everything above. Animate transform and opacity only — never height, top or width on a per-frame path, with the single audited exception of the panel's expand. And no animation may delay an answer: motion decorates state that has already changed, it never gates it.

What I would push back on

Three of these are worth naming before the build rather than after.

Chat can be slower

Transcripts invite reading; wizards invite tapping. If median time-to-verdict rises, the product is worse at its one job no matter how good it feels.

Mitigation: auto-advance on tap removes three Continue presses, so taps should actually go down. Gate stage 3 on the number, not on sentiment.

Voice may die at permission

Mic grant rates on mobile web are frequently under half. Accuracy is irrelevant if most people never get past the browser prompt.

Mitigation: never auto-prompt. The mic is tapped deliberately, a denial is a one-time inline note, and ask_mic_permission measures the cliff before we invest further.

A bad parse is worse than none

Filling four answers wrongly costs more than asking four questions — the person must now find and undo our mistakes.

Mitigation: nulls stay null, every fill is shown as an editable chip, and below 0.5 confidence we do not fill at all. The 85% bar is agreed now, not argued after launch.
